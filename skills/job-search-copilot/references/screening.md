# 条件核实与岗位证据

## 条件逐项判断

| 条件 | 需要核实的内容 | 容易混淆的表述 |
|---|---|---|
| 固定薪资 | 固定、绩效、提成、补贴、税前/税后、试用期 | 招聘范围上限、综合收入、最高可达 |
| 休息 | 每周休几天、固定周末/排班、大小周、值班频率 | 月休八天、弹性休息、法定假期 |
| 办公地点 | 实际楼栋/门牌、驻场/外包地点、是否搬迁 | 注册地址、公司总部、列表商圈 |
| 通勤 | 出门到到岗，高峰候车、换乘、步行、班次 | 只计算地铁乘坐时长、直线距离 |
| 业务 | 实际服务产品、内容对象、销售/引流/直播责任 | 标题叫运营，实质做被排除的业务 |
| 用工 | 合同、工资、社保主体，试用期与项目期 | 客户品牌被误当成签约雇主 |
| 匹配 | 必须技能、作品、岗位经验、学历与替代路径 | 会用AI等同于会开发模型或带团队 |

地区和通勤按用户明确边界处理。用户仅接受某一区域时，不能因邻区更容易找到职位就擅自扩大正式投递范围。

## 证据记录

每项记录 `status`、具体观察、来源和核验时间：

- `pass`：有证据支持满足用户所定义条件，注明薪资/休息口径。
- `fail`：明确不满足。记录原话或页面要点，不继续自动投递。
- `unknown`：未写明、来源冲突、只有旧索引或无法确认；提出具体问题。

官方职位页和HR当前回复优先于搜索摘要。平台标签与正文矛盾、多个薪资口径冲突时保持未知并询问。保存信息只证明当时页面状态，后续失效或变更需重查。

职位重新发布有新的职位ID时，作为新条目处理。旧岗位的双休、薪资、地址和已沟通状态都不能直接继承。跨平台同公司同岗位可标“疑似重复”，但驻场地点、职级或招聘主体不同则可能是独立岗位。

## 搜索策略

优先当前可访问的平台和公司官方渠道，以岗位方向、区域、经验弹性和已有作品筛选。先建立少量高相关候选并核实，发现大量销售/金融/主播误匹配后调整关键词与排除条件。

相邻岗位使用真实能力支撑，例如内容策划、剪辑、内容评测或数据内容岗位。对测试、轮班、外包和产量指标逐岗核实。不能因标题包含AI或薪资较高就认为匹配。

业务不清时描述具体风险信号，不凭空给公司贴违法或诈骗标签。明确落入用户排除范围的岗位直接停止；需要收费、贷款、培训协议、押金或非正常用工的要求交给用户评估，不替用户承诺。

## 通勤做法

先用公开办公地址和用户提供的近似出发点计算工作日早晚高峰路线，给出范围、换乘和步行假设。住所到地铁站的时间未知时明确保留，不将“地铁约四十分钟”写成“门到门四十分钟”。

招聘方只需要了解大致居住区域和到岗可行性。精确家庭地址不放进简历、HR初次沟通或公共仓库。
